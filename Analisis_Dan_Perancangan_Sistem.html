Analisis Modul & Simulasi UAS Interaktif

Mata Kuliah: MSIM4302 - Analisis dan Perancangan Sistem (9 Modul Lengkap)

1. Konsep Inti yang Paling Sering Diulang

Berdasarkan struktur materi dari Modul 1 sampai Modul 9, konsep-konsep berikut merupakan fondasi utama yang terus diulang dan saling bersilangan:

  • SDLC (System Development Life Cycle): Alur hidup pengembangan sistem (Perencanaan, Analisis, Transisi, Desain, Implemetasi) yang menjadi payung waktu seluruh aktivitas analis.
  • Abstraksi Pemodelan (Modeling): Proses penyederhanaan kompleksitas dunia nyata ke dalam diagram grafis terstruktur (DFD/Flowchart) maupun berorientasi objek (UML).
  • Paradigma Berorientasi Objek (OOAD): Cara pandang sistem sebagai kumpulan objek yang saling berinteraksi, bertukar pesan, dan memiliki karakteristik enkapsulasi, pewarisan, serta polimorfisme.

2. Tujuan Pembelajaran Tiap Modul

  • Modul 01: Memahami urgensi pengembangan sistem, prinsip dasar SDLC, dan karakteristik berbagai metodologi.
  • Modul 02: Mengidentifikasi kelayakan proyek sistem (feasibility), manajemen risiko, dan penyusunan jadwal rencana kerja.
  • Modul 03: Menentukan persyaratan sistem (Functional & Non-Functional) melalui teknik elisitasi (Wawancara, JAD, Observasi).
  • Modul 04: Memodelkan aliran data dan proses bisnis terstruktur organisasi menggunakan Context Diagram dan DFD.
  • Modul 05: Memahami paradigma berorientasi objek dan menangkap kebutuhan interaksi pengguna via Use Case Diagram.
  • Modul 06: Memetakan urutan aktivitas bisnis dinamis (Activity Diagram) dan struktur data statis objek (Class Diagram).
  • Modul 07: Menganalisis interaksi berbasis waktu antar-objek (Sequence Diagram) serta perubahan status internal objek (State Diagram).
  • Modul 08: Melakukan transformasi model analisis konseptual ke arsitektur desain fisik database dan memilih opsi akuisisi sistem.
  • Modul 09: Merancang arsitektur fisik perangkat lunak/keras serta mendesain antarmuka pengguna (UI/UX) sesuai prinsip dialog interaktif.

3. Istilah Penting Potensial Soal Esai

  • Requirement Elicitation: Proses mengidentifikasi, mengumpulkan, dan menjaring kebutuhan sistem dari stakeholders.
  • Functional vs Non-Functional Requirements: Kebutuhan fungsional (layanan/fitur sistem) vs Non-fungsional (kualitas operasional seperti performa, kapasitas, enkripsi, dan keamanan).
  • Encapsulation, Inheritance, Polymorphism: Enkapsulasi (pembungkusan data), Pewarisan (penurunan sifat kelas), Polimorfisme (banyak bentuk fungsi).
  • Multiplicity (Kardinalitas): Batasan jumlah hubungan atau keterhubungan antar-entitas/kelas pada Class Diagram dan ERD (contoh: 1..*, 0..1).
  • COTS (Commercial Off-The-Shelf): Strategi pengadaan dengan membeli paket sistem perangkat lunak jadi yang tersedia di pasar umum.

4. Rumus dan Prosedur yang Wajib Dikuasai

  • Prosedur Konsistensi Balancing DFD: Aturan mutlak bahwa input dan output data pada entitas luar di Diagram Konteks harus sama persis jumlah dan jenisnya ketika didekomposisi ke DFD Level 0 dan Level 1.
  • Rumus Analisis Kelayakan Ekonomi: Perhitungan nilai finansial berupa Return on Investment (ROI) dan Payback Period (Periode Pengembalian Modal investasi sistem).
  • Logika Matriks Tabel Keputusan: Mengonstruksi tabel kondisi (Y/T) dan tindakan (X) guna mengeliminasi ambiguitas logika aturan bisnis yang bercabang banyak.

Soal 2: Pemodelan Kebutuhan Fungsional (UML Use Case Diagram) Diagram
Studi Kasus E-Commerce:
Sebuah platform belanja online merancang sistem transaksi baru. Pelanggan dapat bebas mencari produk dan memasukkannya ke dalam keranjang belanja. Namun, ketika Pelanggan akan mengeksekusi proses Checkout dan Melakukan Pembayaran, sistem secara mutlak mewajibkan mereka melakukan Login terlebih dahulu. Di sisi lain, aktor Admin Gudang mengelola stok barang dan melakukan konfirmasi pembayaran.

Buatlah rancangan Use Case Diagram lengkap dengan batasan sistem (system boundary) serta relasi dependensi <<include>> atau <<extend>> secara tepat!

Rancangan Visual Jawaban:

======================= Batas Sistem E-Commerce ======================= | | | ( Mencari Produk ) | | ^ | | | | | (( Pelanggan )) | | | | | v | | ( Mengelola Keranjang ) | | | | ( Melakukan Checkout ) --- <<include>> ---> ( Melakukan Login ) | | ^ | | | | | (( Admin )) | | | | | v | | ( Mengelola Stok ) | | | =======================================================================
Penjelasan Narasi Pendukung Esai:

Diagram di atas mengelompokkan fungsionalitas sistem berdasarkan hak akses aktor. Relasi dari Melakukan Checkout menuju Melakukan Login wajib menggunakan panah putus-putus dengan label <<include>>. Hal ini dikarenakan proses login bukan pilihan opsional, melainkan bagian dari alur wajib yang harus dieksekusi agar proses checkout dapat berjalan.

Soal 3: Pemodelan Struktural Data (UML Class Diagram) Diagram
Studi Kasus Penjualan:
Sebuah entitas bisnis toko pakaian memerlukan pemetaan database berorientasi objek. Aturan bisnis menetapkan: Seorang Pelanggan (atribut: id_pelanggan, nama, alamat) dapat memiliki atau membuat banyak transaksi Pesanan (atribut: id_pesanan, tgl_pesanan, total_harga). Setiap satu transaksi Pesanan dapat memuat atau berisi satu atau banyak item Produk (atribut: id_produk, nama_produk, harga).
Pertanyaan Esai:

Susunlah rancangan Class Diagram yang memuat tiga kelas tersebut, lengkap dengan tipe data atribut, metode operasional, dan angka multiplisitas (kardinalitas) yang logis!

Rancangan Visual Jawaban:

+-----------------------+ +-----------------------+ | Pelanggan | | Pesanan | +-----------------------+ +-----------------------+ | - id_pelanggan: int | 1 * | - id_pesanan: int | | - nama: string |------------------->| - tgl_pesanan: date | | - alamat: string | Melakukan | - total_harga: double | +-----------------------+ +-----------------------+ | + tambahPelanggan() | | + hitungTotal() | +-----------------------+ +-----------------------+ | * | Memuat | v 1..* +-----------------------+ | Produk | +-----------------------+ | - id_produk: int | | - nama_produk: string | | - harga: double | +-----------------------+ | + updateStok() | +-----------------------+
Penjelasan Narasi Pendukung Esai:

Angka 1 pada kelas Pelanggan dan * (many) pada kelas Pesanan menunjukkan batasan hubungan bahwa satu pelanggan dapat berbelanja berkali-kali hingga memicu banyak nota pesanan, namun satu nota pesanan spesifik hanya boleh merujuk pada satu pelanggan tunggal. Hubungan dari Pesanan ke Produk bertanda 1..* karena sebuah nota transaksi tidak boleh kosong (minimal berisi satu item produk yang dibeli).

Soal 4: Analisis Kelayakan Ekonomi (Menghitung ROI & Payback Period) Hitungan
Skenario Proyek IT:
Tim analis merencanakan pengadaan sistem ERP dengan total nilai investasi awal pada tahun ke-0 sebesar Rp 120.000.000. Berdasarkan estimasi, proyeksi keuntungan bersih (manfaat dikurangi biaya operasional berkala) yang akan diterima perusahaan selama 3 tahun ke depan adalah:
  • Tahun 1: Rp 50.000.000
  • Tahun 2: Rp 60.000.000
  • Tahun 3: Rp 40.000.000
Pertanyaan Esai:

Hitunglah secara matematis nilai Return on Investment (ROI) proyek sistem tersebut dan tentukan durasi waktu tepatnya proyek mencapai Payback Period!

Langkah Penyelesaian Ringkas & Sistematis:

1. Menghitung Akumulasi Total Manfaat Bersih

Total Manfaat = Manfaat Thn 1 + Thn 2 + Thn 3
Total Manfaat = Rp 50.000.000 + Rp 60.000.000 + Rp 40.000.000 = Rp 150.000.000

2. Rumus dan Perhitungan ROI
Rumus ROI = ((Total Manfaat - Nilai Investasi) / Nilai Investasi) x 100% ROI = ((Rp 150.000.000 - Rp 120.000.000) / Rp 120.000.000) x 100% ROI = (Rp 30.000.000 / Rp 120.000.000) x 100% ROI = 0.25 x 100% = 25%

Kesimpulan ROI: Proyek pengembangan sistem ini layak karena menghasilkan tingkat pengembalian investasi (keuntungan) sebesar 25%.

3. Perhitungan Payback Period (Waktu Balik Modal)
Nilai Nilai Investasi Awal = Rp 120.000.000 - Keuntungan Tahun 1 = Rp 50.000.000 Sisa Nilai Investasi = Rp 70.000.000 - Keuntungan Tahun 2 = Rp 60.000.000 Sisa Nilai Investasi = Rp 10.000.000 (Sisa ini akan ditutup pada arus kas Tahun 3) PP = 2 Tahun + (Sisa Nilai Investasi / Keuntungan Tahun 3) x 12 Bulan PP = 2 Tahun + (Rp 10.000.000 / Rp 40.000.000) x 12 Bulan PP = 2 Tahun + (1/4) x 12 Bulan = 2 Tahun 3 Bulan

Kesimpulan Payback Period: Nilai pengeluaran kapital investasi awal pembangunan sistem akan kembali modal sepenuhnya dalam kurun waktu 2 tahun 3 bulan.

Soal 5: Logika Proses Terstruktur (Mengonstruksi Decision Table) Logika
Aturan Bisnis Distribusi Barang:
Sebuah perusahaan ekspedisi menerapkan aturan tarif khusus:
  1. Jika pengiriman berstatus "Kilat" dan berat barang > 10 kg, maka dikenakan Biaya Tambahan Utama + Proteksi Asuransi.
  2. Jika pengiriman berstatus "Kilat" namun berat barang ≤ 10 kg, maka hanya dikenakan Biaya Tambahan Utama tanpa asuransi.
  3. Jika pengiriman berstatus "Reguler" dan berat barang > 10 kg, maka hanya dikenakan Proteksi Asuransi.
  4. Jika pengiriman berstatus "Reguler" dan berat barang ≤ 10 kg, maka dikenakan Tarif Dasar Normal (tidak ada biaya tambahan/asuransi).
Pertanyaan Esai:

Petakan kondisi logika penentuan tarif di atas ke dalam struktur Tabel Keputusan (Decision Table) yang baku!

Soal 6: Analisis Komparatif Strategi Akuisisi Sistem Analisis
Studi Kasus Rumah Sakit:
Sebuah instansi pelayanan kesehatan/Rumah Sakit Daerah mendesak membutuhkan modul aplikasi Sistem Informasi Rekam Medis Elektronik dalam batas waktu maksimal 1,5 bulan demi memenuhi syarat akreditasi instansi. Kendala internal yang dihadapi adalah tim IT rumah sakit hanya berjumlah 2 orang dan belum pernah mengembangkan arsitektur basis data medis terenkripsi.
Pertanyaan Esai:

Analisislah pilihan keputusan yang paling bijak di antara 3 pilar alternatif strategi akuisisi sistem (In-House Development, Membeli Paket Jadi/COTS, atau Outsourcing) untuk menyelesaikan problematika rumah sakit tersebut!

Contoh Struktur Jawaban Esai Berbobot Nilai Tinggi:

Pilihan strategi akuisisi sistem yang paling direkomendasikan dan rasional untuk Rumah Sakit Daerah tersebut adalah Membeli Paket Perangkat Lunak Jadi (COTS - Commercial Off-The-Shelf).

Analisis Dasar Pertimbangan Logis:
  1. Batasan Waktu yang Kritis: Tenggat waktu akreditasi sangat mepet (1,5 bulan). Jika memilih jalur In-house development atau Outsourcing, durasi waktu tersebut habis hanya untuk fase elisitasi kebutuhan dan penulisan dokumen kontrak kerja sama. Paket software COTS siap pakai dapat langsung diinstalasi dan dikonfigurasi dalam hitungan hari.
  2. Keterbatasan Kompetensi SDM Internal: Staf IT internal yang minim pengalaman tidak akan mampu merancang sistem medis dengan standar enkripsi yang aman dari kebocoran data dalam waktu singkat. Pembelian COTS memberikan keuntungan berupa pemanfaatan sistem yang sudah matang dan diuji stabilitasnya oleh pasar.
  3. Kesesuaian Standar Regulasi: Paket aplikasi rekam medis komersial umumnya dikembangkan dengan mengikuti standar aturan Kementerian Kesehatan terbaru, sehingga mempercepat pemenuhan poin penilaian tim akreditasi nasional.
Soal 7: Konsep Desain Antarmuka Dialog (Window Navigation Diagram) Desain UI/UX
Pertanyaan Esai:

Dalam tahap transisi analisis menuju desain antarmuka, jelaskan apa fungsi utama dari pembuatan User Interface Structure Diagram atau yang dikenal sebagai Window Navigation Diagram (WND) serta sebutkan dampak buruk yang terjadi jika tahap ini dilewati begitu saja oleh tim pengembang!

Contoh Struktur Jawaban Esai:

Fungsi Utama Window Navigation Diagram (WND):
WND berfungsi sebagai cetak biru tata letak arsitektur interaksi pengguna yang memetakan seluruh komponen jendela, halaman, atau menu dalam aplikasi. Diagram ini memperlihatkan secara jelas arah pergerakan arus navigasi dari satu tampilan layar ke tampilan layar lain yang dipicu oleh aksi respon tertentu (misalnya, klik tombol, geser layar, atau ketik input).

Dampak Buruk Jika Mengabaikan WND:
  • Munculnya Dead-End Pages (Halaman Buntu): Aplikasi berisiko memiliki halaman tertentu yang tidak menyediakan tombol kembali (back) atau tombol navigasi keluar, sehingga memaksa pengguna menutup paksa sistem akibat terjebak.
  • Inkonsistensi Alur Aplikasi (Bad UX): Alur perpindahan menu menjadi membingungkan karena tidak ada standarisasi rute, menurunkan tingkat kenyamanan pengguna baru dalam mengoperasikan sistem.
  • Pemborosan Waktu Pengodean (Coding Redundancy): Programmer terpaksa melakukan pembongkaran kode struktur rute berkali-kali karena baru menyadari adanya kesalahan logika navigasi setelah aplikasi dirakit setengah jalan.
